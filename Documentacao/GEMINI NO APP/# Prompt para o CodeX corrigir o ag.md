O comportamento atual está errado porque o agente:

* inventa métricas (gastos, cliques, conversões etc.) sem base em dados reais das APIs;
* mistura períodos diferentes do que o usuário pediu (ex.: usuário pede 15 dias, ele responde 7 dias);
* inventa IDs de conta e mensagens de erro de API;
* expõe detalhes internos (como `hours_today`) que não fazem sentido para o usuário final.

Seu objetivo é garantir que **TUDO o que o agente disser sobre métricas, contas, datas e IDs venha 100% das ferramentas / APIs integradas (MCPs)**, ou seja, Google Ads, Meta Ads, GA4 etc., ou então seja claramente rotulado como “não sei / não consegui consultar”.

---

## 1. Proibir números/IDs inventados

Aplique as regras abaixo no **prompt de sistema do Gemini** e, se necessário, também na lógica de backend:

1. O agente **só pode falar de métricas numéricas** (gasto, impressões, cliques, CTR, CPC, CPM, conversões, valor de conversão, mensagens iniciadas, leads etc.) se **esses campos existirem explicitamente** no JSON retornado pelas ferramentas (Meta Ads, Google Ads, GA4 etc.).
2. Se **nenhuma ferramenta foi chamada** ou se a chamada **falhou**, o agente deve responder **sem números e sem IDs inventados**, com frases simples, por exemplo:

   * "Não consegui consultar os dados de Meta Ads para esse período." ou
   * "A API do Google Ads retornou erro ao buscar o cliente informado."
3. O agente **não pode inventar**:

   * `account_id` de Meta Ads,
   * `customer_id` de Google Ads,
   * nomes de variáveis internas (`hours_today`, nomes de tabelas etc.),
   * nem textos de erro que não vieram da API.
4. Ele só pode mencionar mensagens de erro/textos que o backend realmente recebeu da API e **enviou explicitamente** para o modelo.

---

## 2. Uso obrigatório de ferramentas (MCP / tool use)

Configure o agente Gemini para que **toda pergunta sobre dados de campanha use ferramentas obrigatoriamente**:

1. Ative a configuração equivalente a **`tool_choice = required`** (ou similar, dependendo do SDK do Gemini) para esse agente de analytics.
2. Toda pergunta que envolva:

   * desempenho de campanha,
   * resumo de resultados,
   * gastos, cliques, leads, conversões,
     deve **disparar funções/ferramentas** de:
   * Meta Ads (conta da Aviarte),
   * Google Ads,
   * GA4 (se estiver integrado).
3. O agente **nunca** deve responder consultas de performance usando apenas "conhecimento geral" do modelo. Se não houver dados de ferramenta, ele deve dizer **claramente** que não conseguiu consultar.

---

## 3. Datas relativas (ex.: “últimos 15 dias”) resolvidas no backend

Para reduzir alucinação, o Gemini **não deve interpretar datas relativas**. Isso deve ser feito **no backend**, por você (CodeX):

1. No backend, antes de chamar qualquer ferramenta, transforme expressões do usuário como:

   * "últimos N dias",
   * "últimos 7 / 30 dias",
   * "ontem", "mês passado",
     em `start_date` e `end_date` explícitos, usando o timezone padrão do app (`America/Sao_Paulo`).
2. Passe para as ferramentas **e para o modelo** sempre datas explícitas, por exemplo:

   ```json
   {
     "start_date": "2025-11-19",
     "end_date": "2025-12-03"
   }
   ```
3. No prompt de sistema do Gemini, inclua uma instrução clara:

   > "Não interprete datas relativas por conta própria. Use sempre as datas explícitas (`start_date` e `end_date`) que o backend te enviar."

---

## 4. Período da resposta tem que bater com o período consultado

1. Se o usuário pedir "**últimos 15 dias**", o agente **não pode** responder "últimos 7 dias" ou qualquer outro período diferente.
2. O período exibido na resposta deve ser **exatamente o mesmo** que o backend usou na consulta às APIs (datas já calculadas).
3. Instrução para o prompt de sistema do Gemini:

   > "Sempre deixe claro o período analisado na sua resposta, usando exatamente as datas que o backend forneceu. Ex.: `Período analisado: 19/11/2025 a 03/12/2025`."

---

## 5. Fluxo de erro simples e confiável (Meta Ads e Google Ads)

No backend, **normalize os erros da API** antes de enviá-los ao modelo. Exemplo de formato:

```json
{
  "source": "meta_ads",
  "status": "error",
  "error_code": "INVALID_ACCOUNT_ID",
  "error_message": "O ID de conta informado não existe ou não está acessível."
}
```

Depois, ajuste o prompt de sistema do Gemini com algo assim:

> "Se `status = "error"` para uma fonte (ex.: `meta_ads`, `google_ads`), **não crie números nem invente detalhes**. Explique o erro de forma curta e, se fizer sentido, peça para o usuário conferir o ID ou as permissões daquela conta. Nunca misture erros de API com métricas numéricas inventadas."

Regras adicionais:

1. Se `status = "error"`, **não retornar métricas** daquela fonte na mesma resposta.
2. Se uma fonte falhar (ex.: Google Ads) e outra funcionar (ex.: Meta Ads), deixar isso claro, sem tentar "preencher" o que faltou.

## 6. Proibir “fonte” e IDs falsos

1. O agente só pode escrever coisas do tipo:

   * "Fonte: Meta Ads"
   * "Fonte: Google Ads"
     se realmente houver **dados válidos** dessa fonte presentes na mensagem que o backend envia para ele.
2. Se o backend não mandou `account_id`, o agente **não deve inventar**.
3. Remova do prompt atual qualquer instrução do tipo **"seja proativo"** ou "complete com o que achar razoável" no que diz respeito a:

   * IDs de conta,
   * métricas numéricas,
   * mensagens de erro.

---

## 7. Não expor detalhes internos

O agente não deve mencionar coisas internas do sistema para o usuário, como:

* nomes de variáveis (`hours_today`),
* nomes de tabelas ou coleções,
* nomes de MCPs internos,
* estrutura de payload.

Instrução para o prompt de sistema:

> "Nunca mencione nomes de variáveis internas, nomes de tabelas ou detalhes técnicos do backend. Escreva sempre como se você fosse um analista de marketing conversando com o cliente."

## 8. Formato padrão de resposta para relatórios de campanha

Defina, no prompt de sistema, um formato simples e consistente para as respostas do agente, por exemplo:

1. **Período analisado:**

   * Ex.: `Período analisado: 19/11/2025 a 03/12/2025.`
2. **Plataforma por plataforma:**

   * **Meta Ads:** listar apenas métricas realmente disponibilizadas pelo JSON recebido.
   * **Google Ads:** idem.
3. **Resumo interpretativo curto:**

   * O que melhorou, o que piorou, onde estão os principais resultados.
4. **Próximos passos sugeridos (opcional):**

   * Ex.: "Testar novo criativo, aumentar orçamento em tal campanha", etc.

Se faltar alguma plataforma (por erro ou ausência de dados), o agente deve indicar isso claramente:

* "Meta Ads: dados retornados com sucesso."
* "Google Ads: não foi possível consultar, a API retornou erro de `customer_id inválido`."

Sem inventar números para "preencher" o relatório.
